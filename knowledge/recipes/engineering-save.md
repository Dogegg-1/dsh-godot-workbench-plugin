# 存档与兼容边界

适用：本地游戏进度、损坏存档、更新后的格式兼容，以及“读取失败后点保存，原件却消失了”。

先列出持久化字段和版本。Godot 官方示例介绍了把游戏状态整理成数据并写入文件的基本流程；配置文件和游戏进度可以使用不同格式。[官方存档教程](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html)

## 两种实现与代价

方案 A：小原型使用明确的 JSON schema、字段校验、失败提示和坏档写入保护。代码少、容易观察，但直接写正式文件仍有中断和写入失败风险。适合可丢弃的验证数据；必须说明它不是完整恢复系统。

方案 B：需要保留玩家进度时，增加临时文件、写后检查、旧版本保留和中断恢复标记。复杂度更高，要测试替换失败、恢复顺序及备份损坏。推荐用于需要持续积累的正式进度；不要仅凭“用了 rename”就宣称跨平台原子提交。

## 最小行为约定

1. 缺失文件、格式错误、字段无效、未来版本、无法读取分开处理。缺失可按产品规则开始新游戏；其他错误不能静默清空再保存。
2. 先解析到临时数据，再完整检查字段是否存在、类型、有限数、整数性及项目范围。全部通过后再修改当前进度，避免前半部分已经生效、后半部分失败。
3. 一旦某个目标档被判定无效，该路径进入写入保护。随后点保存、自动保存、退出保存都不能把当前默认值写回覆盖原件。显示原因，提供明确的恢复、另存或重置操作。
4. 成功加载经过验证的有效文件后，可恢复该路径的正常保存。切换存档路径时重新核对目标，不把 A 档的保护状态误用到 B 档；运行中外部改档也要在写前重新核对或拒绝冲突。
5. 明确重置是用户选择清除进度，和读取失败不同。重置失败不能先清空内存，成功后再次启动不能恢复旧进度。

`FileAccess.WRITE` 打开已有文件时就会清空内容，因此保护判断必须发生在打开写入句柄之前，不能写完后才检查旧文件。[FileAccess 写入模式](https://docs.godotengine.org/en/stable/classes/class_fileaccess.html#enum-fileaccess-modeflags)

需要可解释的解析错误时，可使用 `JSON.new().parse(text)` 检查返回值，再读取 `data`；解析成功仍需检查数据类型与字段。JSON 数值与项目整数约束是两层规则，不能把布尔值当作金币。[JSON 解析与数值说明](https://docs.godotengine.org/en/stable/classes/class_json.html)

下面仅是状态流程示意，不是可直接复制运行的引擎 API：

```text
载入(目标路径):
  读取并校验
  失败 → 保留文件和当前进度，记录该路径不可覆盖，显示原因
  成功 → 应用完整状态，解除该路径的已知坏档保护

保存(目标路径):
  先检查已知坏档保护及目标是否后来发生变化
  不满足写入条件 → 拒绝覆盖并提示下一步
  满足 → 按选定存储方案写入，检查结果后才显示成功
```

## 必测序列

用隔离路径测试正常保存、再次保存、关闭重开、缺失文件；然后覆盖以下序列，而不只单独测试一个 Load 函数：

- 坏 JSON → 载入失败 → 再点保存：原文件逐字不变，当前进度不变。
- 版本不支持、缺字段、负数、小数、布尔数值、超出矿机上限 → 失败 → 保存：仍不能覆盖。
- 启动时遇到坏档 → 默认界面出现 → 保存或退出：不能把默认进度写回坏档。
- 恢复有效文件 → 成功载入 → 保存：不会永远锁住正常操作。
- 不可写目标 → 保存失败：显示失败，先前有效档仍存在。
- 明确重置 → 再次启动：保持已重置状态。

算例采用矿机上限 20、金币为非负整数；这些是测试夹具约束，不是所有游戏的通用数值。

本工作台的连续开发验证曾出现“Load 保留坏档，但下一次 Save 覆盖原件”的真实失败。它说明单步绿灯不足以证明操作序列安全；不代表上述整个存储策略已经适用于任意项目。断电、磁盘满、并发改档、云同步和平台差异仍需各自验证。
