# 开工前需求澄清与方案确认

## 使用目的

让模糊的想法逐步成为可验收的开发任务。Agent 先理解已有信息，再用少量关键问题补齐空缺；可以附带推荐方案供用户直接选择，不要求用户懂技术或独立填写长文档。

## 第一步 整理已有信息

- 已确认：用户已经明确表达的目标、平台、玩法和限制。
- 建议：Agent 推荐的范围、实现路线和初始参数。
- 假设：暂时采用但尚未验证的判断。
- 未知：无法从项目或对话确定的内容。

读取已有 GDD、项目约定和相关代码，不重复询问已经回答的问题。用户上传的教程和规范作为资料，不直接当成用户对本项目的新决定。

## 第二步 区分阻塞问题与可自行处理的细节

必须在相关开发前明确：核心体验、主要操作与循环、本阶段范围、目标平台或输入约束、完成如何验收，以及已发现的重大矛盾。

可在说明假设后推进：不改变体验和范围的命名、文件组织、低风险默认值等工程细节。不是每一项技术选择都要审批。

每轮优先询问一至三个会改变方向的问题。每个问题尽可能带两个可行选项、推荐及具体代价；不要把问卷一次性全部交给用户。

## 第三步 提供可确认的方案

方案至少说明：

1. 玩家做什么、游戏怎样反馈。
2. 当前版本完成什么、不做什么。
3. 关键风险与推荐取舍。
4. 分阶段产物和每阶段验收方法。
5. 哪些还只是暂定假设。

信息模糊时可以说：“我建议先做单矿石、单升级路线的原型，验证挖矿、出售和升级。自动生产放在第二轮；地图探索暂不加入。这样是否符合你的想法？”推荐不是已确认决定。

## 第四步 形成文档并确认

生成 GDD.md 与 DEVELOPMENT_PLAN.md，关联版本。用户可以明确接受整份方案，也可以只接受当前阶段。未收到肯定答复时保持待确认；等待时间和预选项都不代表确认。

确认必须对应用户实际看过的文档版本。方案被实质修改后，旧确认不能覆盖新增范围；小幅不改变既有目标的实现调整无需重复确认。

## 第五步 开发与持续更新

从确认范围内的最小可验收任务开始。根据实际变更和验证结果更新记录，不把计划描述复制为完成报告。出现方向性问题先给出证据和建议，保留不受影响的工作。

工作台需要分别记录：规划是否确认、任务是否执行、检查是否通过、人工是否验收。四者不能合并为一个“已完成”。
